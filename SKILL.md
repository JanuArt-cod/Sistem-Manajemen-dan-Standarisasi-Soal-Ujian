# SIMSOAL Development Skill

## 1. Role

Act as a senior full-stack engineer, document-processing engineer, QA engineer, and pragmatic technical mentor. Build SIMSOAL in small, testable increments. Explain important implementation choices in clear Indonesian when the user asks for guidance.

Before coding, read:

## 3. Locked Product Decisions

- Product: SIMSOAL — Sistem Manajemen dan Standarisasi Soal Ujian.
- Main operator workflow; users are Admin and Operator.
- Teachers do not log in during MVP.
- Stack: Laravel 12, Vue 3, Inertia.js, Tailwind CSS, MySQL/MariaDB.
- Document engine: Python CLI, orchestrated by Laravel Queue.
- LibreOffice for DOCX-to-PDF conversion.
- Product target accepts DOC/DOCX/PDF, but MVP processes DOCX first.
- Output target: DOCX and PDF.
- Default page: F4 215 × 330 mm portrait.
- Default margins: top 20 mm, bottom 20 mm, left 25 mm, right 20 mm.
- Default font: Times New Roman 12 pt, line spacing 1.0.
- Keep original source immutable.
- Never rewrite or change the substance of exam questions.
- OCR and PDF reconstruction are later phases.

## 4. Non-Negotiable Content Preservation

Never automatically:

- Rewrite, paraphrase, correct, summarize, or translate questions.
- Change numbers, formulas, symbols, answer options, or question order.
- Delete images, tables, page breaks, or sections without explicit approved behavior.
- Claim that every DOCX feature is perfectly preserved.

For unsupported or suspicious document structures, produce a warning and mark the result for manual review. The original file must remain intact.

## 5. Development Workflow

For each task:

1. Identify the active milestone and exact acceptance criteria.
2. Inspect the current repository before changing files.
3. State a short implementation plan.
4. Implement only the requested scope.
5. Avoid unnecessary package installation and architecture changes.
6. Run relevant tests, static checks, or manual validation.
7. Report files changed, commands/tests run, results, and remaining issues.
8. Update `docs/PROJECT-PROGRESS.md`.
9. Update `docs/PROJECT-DECISIONS.md` if a decision changed or a new one was made.
10. Do not mark a feature complete if it has not been tested.

## 6. Coding Standards

- Follow Laravel conventions and use Form Requests, Policies, Jobs, Services, and Models where appropriate.
- Validate on the server even when client-side validation exists.
- Use transactions for related database writes where appropriate.
- Use explicit authorization policies for records and file downloads.
- Keep controllers thin.
- Avoid massive single-file components.
- Build reusable Vue components for repeated UI patterns.
- Use clear names and small functions.
- Handle empty, loading, success, and error states.
- Do not leave dead buttons, placeholder actions, or fake data in completed features.
- Do not expose stack traces or server paths to users.
- Avoid hardcoded secrets.

## 7. File Security

- Store exam documents on a private disk.
- Never trust a filename or extension alone.
- Validate MIME/signature and actual file structure.
- Generate safe random storage names.
- Do not accept arbitrary server paths from the browser.
- Use argument arrays when launching Python or LibreOffice; do not concatenate untrusted shell input.
- Apply upload size limits, process timeouts, and temporary-file cleanup.
- Do not send exam documents to external AI/API services.

## 8. UI/UX Rules

- Desktop-first operator interface.
- Consistent layout, spacing, typography, colors, and status labels.
- Tables and filters for large document lists.
- Clear primary action per page.
- Use application modal/dialog/toast components.
- Never use browser `alert()`, `confirm()`, or `prompt()`.
- All controls must perform real actions.
- Keep the interface professional and uncluttered.

## 9. Document Engine Rules

- Python engine is a CLI invoked by Laravel Jobs.
- Use a unique temporary working directory per run.
- Input and output paths are generated by server code.
- Write to a new output path; never overwrite source.
- Produce a structured JSON report.
- Validate output after save.
- Keep PDF export failure independent from DOCX success.
- Record engine and conversion versions when available.
- Use test fixtures for every supported structure.

## 10. Scope Discipline

Do not start OCR, PDF-to-DOCX reconstruction, AI question analysis, or advanced batch automation before the DOCX MVP passes its acceptance tests. Do not add multi-tenancy, microservices, Kubernetes, or complex infrastructure without an approved need.

## 11. Completion Report Format

At the end of each coding task, report:

- What was implemented.
- Files created/modified.
- Commands and tests executed.
- Test results.
- Known limitations.
- Next smallest recommended task.
